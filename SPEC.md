## 0. The one-paragraph summary

Carnatic raga identity lives substantially in the *continuous* pitch contour —
the gamaka (ornamentation) — not only in the discrete note set. The **spine** of
this project is a **quantisation study**: measure how raga classifiability decays as
pitch resolution is coarsened from continuous cents down to 12 semitones. If the
accuracy collapses as resolution coarsens, that quantifies how much raga identity
lives below the note level. On top of that spine sit two smaller pieces: an
**allied-raga contrast** (ragas that share a note set but differ in gamaka) and an
**optional small generative model** of pitch contours. The generator is a
proof-of-concept only and must not block submission.

## 1. Hard constraints (read first, do not violate)

1. **Compute:** everything must run on **Kaggle / Colab free tier** (single T4 or
   P100, ~12–16 GB GPU RAM, ~12 h session cap, ephemeral disk). No multi-GPU, no
   assumptions of a persistent filesystem. Checkpoint early and often. Keep models
   small (≤ ~5–10M params for the generator).
2. **Deliverable:** a report + runnable notebooks + code. The **report content**
   (figures, tables, numbers) is generated by the notebooks and collected into a
   final summary notebook / markdown.
3. **Artist confound is a first-class constraint.** See §3. Every raga-level result
   must be reported alongside the artist composition behind it. Never make a claim
   of the form "the model distinguishes raga X from raga Y" when singer identity
   could equally explain it. State this limitation explicitly wherever it applies.
4. **Splitting discipline:** never let windows from the *same recording* fall on
   both sides of a train/test split. Split by recording (and where possible by
   artist). A random window split is a bug, not a shortcut.
5. **Two representations, kept distinct** (do not conflate):
   - **Folded pitch-class** (`cents % 1200`) — for histograms and classification.
     Raga identity is octave-invariant.
   - **Unfolded cleaned contour** — for the generator, because melodic *shape* and
     gamaka are what it must learn, and folding destroys shape.
6. **No fabricated numbers, ever.** If something can't be computed, say so in the
   status report rather than filling in a plausible value.

  Ask the user for the Kaggle dataset mount path once they've uploaded it.

### 2.3 Annotation file formats (VERIFIED — trust these)
Per recording, in one folder, tab-separated `.txt` files and one `.json` metadata:
- `*.pitch.txt` — 2 columns: `time` (s), `frequency` (Hz). **Frame rate ≈ 225 Hz.**
  Unvoiced frames are `frequency == 0`. Typical voiced fraction ~0.7.
- `*.pitch-vocal.txt` — same format, extracted from the isolated vocal track
  (cleaner) but present for only ~56 recordings.
- `*.ctonic.txt` — single float: the tonic frequency (Hz). **Every cents conversion
  is relative to this.** `cents = 1200 * log2(freq / tonic)`.
- `*.sections-manual-p.txt` and `*.sections-manual.txt` — **4 tab-separated columns:**
  `start_time`, a constant `1`, `duration`, `label`. NOTE: column 3 is DURATION, not
  end time. `end = start + duration`.
  - There are **two** section-file variants (`-p` = 119 files, plain = 73). They may
    cover different recordings. **Milestone 0 must resolve whether merging them
    (deduplicated) increases usable coverage.**
- `*.mphrases-manual.txt` — melodic phrase annotations (timestamps + solfège), present
  for ~117 recordings. Optional; a possible better generation unit than fixed windows.
- Metadata `.json`: raga under key `raaga` (list of dicts, `[0]["name"]`); artist under
  `album_artists` or `artists` (`[0]["name"]`). **Verify these keys against a real file
  before relying on them.**

### 2.4 Section label vocabulary (VERIFIED)
Labels use Unicode diacritics. Alapana appears as **`Vocal ālāp`** and **`Violin ālāp`**
(note the ā and the macron). **Use vocal only; exclude violin.** Match on substring
`"ālāp"` (case-insensitive) AND exclude `"violin"`. Other labels: `Pallavi`,
`Anupallavi`, `Caraṇam`, `Kalpanā svara`, `Nereval`, `Muktāyi svara`, `Tāni āvartana`,
`Ciṭṭa svara`, etc. These are metered/multi-instrument sections.

### 2.5 Pitch-cleaning (VERIFIED necessary — see the raw data)
Raw pitch tracks have TWO problems visible on inspection:
- **Octave errors:** isolated frames that jump ~±1200 cents from neighbours (tracker
  failures). Remove via a rolling-local-median filter: drop frames whose cents value
  is > ~900 cents from the local median over a ~50-frame window.
- **Multi-octave spread:** singing spans >1 octave, so for pitch-class work fold with
  `cents % 1200`. Keep unfolded (cleaned) contour for the generator.

## 3. The artist-confound situation (CRITICAL — this shapes every claim)

The alapana corpus that clears "≥15 min, ≥2 artists" has only 4 ragas, and TWO of
them are effectively single-artist:

| Raga            | total min | artist balance                                  | usable? |
|-----------------|-----------|-------------------------------------------------|---------|
| Karaharapriya   | ~20       | KP Nandini 10.4 / V. Shankaranarayanan 9.8      | **YES — balanced** |
| Mōhanaṁ         | ~16       | Ashwath Narayanan 8.0 / Sumithra Vasudev 7.9    | **YES — balanced** |
| Bhairavi        | ~13       | Vignesh Ishwar 12.3 / Sanjay 0.3                | NO — single-artist |
| Ṣanmukhapriya   | ~12       | Sanjay 12.0 / Akkarai Sisters 0.5               | NO — single-artist |

Consequences, to be respected in code and in the report:
- **The generator** trains cleanly only on the 2 balanced ragas (Karaharapriya,
  Mōhanaṁ). It may generate from all 4 for illustration, but raga-learning claims
  hold only where data is balanced.
- **The allied-pair experiment** cannot use Bhairavi vs Karaharapriya (Bhairavi is
  one voice) without confounding raga with singer. Milestone 0 must **search the full
  collection for an allied AND artist-balanced pair**; if none exists, **drop the
  allied framing** and make the point through the quantisation curve alone.
- **The quantisation study** uses ALL raga-labelled recordings (~185, many artists),
  so the confound is diluted across the collection. This is precisely why it is the
  spine. Run it over every raga with ≥2 recordings from ≥2 artists.

## 4. Project structure (notebooks to produce)

Create these as separate `.ipynb` files under `D:\DGM\notebooks\`. Each notebook sets
a `DATA_ROOT` at the top, is independently runnable, and writes its outputs
(arrays, figures, CSVs) to `D:\DGM\artifacts\` so later notebooks consume them.

- `00_data_audit.ipynb` — inventory, format verification, section-file merge question,
  coverage tables, allied-pair search. **No modelling.**
- `01_corpus_build.ipynb` — build/refresh the cleaned cents corpus (unfolded + folded),
  for both alapana-only and all-vocal-sections variants; write manifests; report
  per-raga and per-artist minutes.
- `02_quantisation_study.ipynb` — THE SPINE. Classifier over ragas at descending pitch
  resolutions; accuracy-vs-resolution curve; recording-grouped splits; artist-aware
  reporting.
- `03_allied_pair.ipynb` — the allied contrast IF a balanced pair was found in M0;
  otherwise a short notebook documenting why it was dropped and pointing to the
  quantisation curve.
- `04_generator.ipynb` — OPTIONAL. Small 1-D contour generative model on the 2 balanced
  ragas; evaluate by pitch-class-histogram distance and classifier-called-raga.
- `05_report.ipynb` — collects every figure/table/number into a single narrative with
  the limitations section. This is the submission summary.

Shared code (loaders, cents conversion, cleaning, splitting) goes in a `dgm_utils.py`
imported by the notebooks — do not copy-paste the pipeline into each notebook.

## 5. Milestones & the 48-hour plan

The user works ~in blocks and will submit a **status report every 6–8 hours**. Design
the work as **7 milestones**, each ending at a natural report boundary with concrete,
checkable outputs. At each milestone, produce a short `STATUS_Mn.md` in
`D:\DGM\status\` containing: what was done, key numbers/figures, what's blocked, what's
next, and any decision you need from the user. **Never end a milestone on a claim you
haven't verified by running the code.**

Timeline assumes intermittent work over 48 h, not 48 h continuous. Training runs are
short (minutes to ~1–2 h on T4) and happen while the user is away.

### Milestone 0 — Data audit & scope lock  (target: 0–6 h) — `00`, start of `01`
Goal: remove every remaining data risk before modelling.
- Verify JSON keys (`raaga`, `album_artists`) against real files.
- Resolve the **section-file merge**: do `sections-manual-p` and `sections-manual`
  together increase usable alapana coverage / artist balance vs the plain file alone?
  Report the delta.
- Rebuild coverage tables (alapana-only AND all-vocal-sections) with per-artist minutes.
- **Allied-pair search:** across all ragas with usable data, list candidate pairs that
  (a) share a note set / are musically allied and (b) have ≥2 artists each with
  reasonable balance. If a good pair exists, name it. If not, recommend dropping the
  allied framing.
- **Decision point for the user:** confirm the final raga set for (i) quantisation,
  (ii) allied pair or its removal, (iii) generator.
Acceptance: coverage tables printed; merge question answered with numbers; allied-pair
recommendation made; `STATUS_M0.md` written asking the user to confirm scope.

### Milestone 1 — Corpus + utils solid  (target: 6–12 h) — `01`, `dgm_utils.py`
- `dgm_utils.py`: loaders, cents conversion, octave-outlier cleaner, fold, recording-
  grouped splitter, windower. Unit-check on a couple of tracks (print voiced %, frame
  rate, a folded histogram with sharp peaks and a strong peak near 0 = Sa).
- Build both corpora (alapana-only; all-vocal-sections) as cleaned `.npy` + manifests.
- Sanity figure: folded pitch-class histogram per raga; confirm peaks land near
  expected swara positions. If a tonic looks wrong (smeared histogram), flag that track.
Acceptance: corpora on disk; per-raga/per-artist minute tables; clean folded histograms;
`STATUS_M1.md`.

### Milestone 2 — Quantisation study runs end-to-end  (target: 12–20 h) — `02`
- Window the folded pitch-class contours (start with ~3–5 s windows; make it a param).
- Baseline classifier (start simple: histogram-feature classifier, e.g. per-window
  pitch-class distribution → logistic regression / small MLP; optionally a small 1-D
  CNN on the windowed contour). Recording-grouped CV.
- Quantisation sweep: continuous → 50c → 20c(? order it sensibly, fine→coarse) →
  100c → semitone (1200/12). Plot **accuracy vs resolution** with error bars over folds.
- Report accuracy per raga AND note artist composition; discuss confound.
Acceptance: the accuracy-vs-resolution curve exists and is the headline figure;
per-fold numbers saved; `STATUS_M2.md` states whether the collapse hypothesis held.

### Milestone 3 — Allied pair (or documented drop)  (target: 20–26 h) — `03`
- If a balanced allied pair was found: restrict to it, show that note-set-level features
  barely separate them while fine-resolution features do; ideally a
  **leave-one-artist-out** check so the separation can't be pure voice.
- If not: write the short notebook documenting the confound and deferring to M2's curve.
Acceptance: either a clean allied-pair result with an artist-controlled check, or a
crisp written justification for dropping it; `STATUS_M3.md`.

### Milestone 4 — Generator v0  (target: 26–34 h) — `04` (OPTIONAL, may slip)
- Small 1-D generative model over UNFOLDED cleaned contours, 2 balanced ragas, raga as
  a conditioning label. A compact diffusion/flow model OR (fallback) an autoregressive
  model over lightly quantised pitch — whichever trains stably first on free-tier.
- Keep it tiny; get *a* working sampler before improving quality.
Acceptance: model trains without diverging; can sample contours conditioned on raga;
checkpoints saved; `STATUS_M4.md`. If unstable after a reasonable attempt, **stop and
mark the generator as a documented negative** — do not let it consume M5/M6.

### Milestone 5 — Generator evaluation  (target: 34–40 h) — `04`
- Evaluate generated contours by: folded pitch-class-histogram distance to real target-
  raga contours; and whether the M2 classifier calls generated samples the right raga.
- Memorisation check: nearest-neighbour (e.g. DTW or simple distance) of generated vs
  training contours, to rule out copying (small corpus → real risk).
Acceptance: histogram-distance table, classifier-on-generated numbers, memorisation
check; honest framing as proof-of-concept; `STATUS_M5.md`.

### Milestone 6 — Report assembly & polish  (target: 40–48 h) — `05`
- Collect all figures/tables into `05_report.ipynb` with narrative: motivation →
  quantisation result → allied contrast (or its absence) → generator PoC → **limitations
  (artist confound, mix-vs-vocal pitch, tiny corpus, single dataset)** → licence note.
- Clean notebooks so they run top-to-bottom on a fresh kernel. Pin package versions.
- Final `STATUS_M6.md`: submission-ready checklist.
Acceptance: every notebook runs clean; report notebook self-contained; limitations
section present and honest.

**Fallback ordering if time is short:** M0, M1, M2, M6 constitute a complete,
submittable project on their own (quantisation study + report). M3 and M4/M5 are
enhancements. Protect the spine.
